# Overview
The follwing directory includes srcipts for setting up database schema, logging chats, and setting up connections to the 
database server. Handling everything databse related. 

-----

# Design
MongoDB is chosen here because it a flexible, document oriented NoSQL database that is best suited for storing unstructured data
such as  chat logs and AI performance metrics. MongoDB allows storing of nested JSON-like objects such as user messages,
LLM responses, timestamps,and other metadata. This flexibility makes it easier to evolve the schema as new metrics are added
overtime. Additionally, the schema less design integraes smootly with Node.js and React as they already use JSON like objects.
The schema less design also allows for faster iterations during development.

# Startup
- To start the MongoDB server, go to the ./database directory and run the following command:
- cmd: sudo systemctl start mongod

#File: dBSetup.js
This script sets uo the databse schema and also contains the hashing function

Hashing Function:
- Hashes user messages and LLM replies for privacy. 
- Currently both raw data and hashed data are being stored for development purposes, but the raw data can be dropped later.
- All mesages are hashed using SHA-256 function
- The hashing key is stored in the .env file
- The hashing function returns a 256-bit hex value
 
Database Schema:

The schema primarily consists of mandatory and optional fields. For the optional fields if no data is provided, the field
is by populated with a default value of -1. The schema is designed such that additional fields can be added as the application
 develops

Mandatory fields:
- conversationId: uuid generated by React frontend for each new chat session
- messageId: uuid generated by dB schema when creating a new document to index documents
- userMessage:
  - raw: raw message text
  - hashed: hashed mesage
  - charLength: calculated automatically by dB, representing the char length of the user message
  - timeStamp: Datetime at whcih the POST request was made to the LLM API
- llmResponse:
  - raw
  - hashed
  - charLength
  - timeStamp: Datetime at which the LLM response was recieved by the middleware server
- modelName: model used to generate the response (important as the middleware is designed to be easily switched to any LLM
 API)

Optional Fields (default -1)
- tokenUsage:
  - input: number of tokens used for user message
  - output: number of tokens used for LLM response
  - total: total tokens used -> input + output
- apiParams: (more can be added if needed)
  - temperature
  - topP
  - topK
  - max_tokens
  - frequency_penality
  - presence_penality
- performanceMetrics: (more advanced metrics will be added later)
  - latencyMs: measured at the middleware server, not end to end latency
  - speedTokensPerMin: average token generation speed per message

- Additional timestamps include:
  - createdAt: datetime at which the document is created, automatically generated by dB
  - updatedAt: datetime at which the document is last modified, to keep track of changed, automatically generated by dB

# File: logChats.js
This files creates a new document for each message intercepted by the middleware server, with the fields logged by the 
middleware. This logChat function is exported to the moddileware script.

- Imports hashMessage function from dBSetup.js to hash user messages and llm responses
- If there is an error logging, the process exits with an error message on the console " Error logging chat: "
- Logging is a critical step for the application
- If the logging is succesful the console reads: "Chat logged: message_id"

Params Logged: 
- conversationId
- userMessage
- hashedUser
- llmResponse
- hashedLLM
- startTime
- replyTime
- modelName
- tokenUsage object
- apiParams object

# File connectDB.js
This srcipt establishes a connection to the MongoDB and return a connection object

- Reads custom MongoDB Port number from env file, throws an error if missing
- The database is named "llm_metrics"
- After a successful connection, the console reads: Connected to MongoDB at 192.2.168.128:PORT#/llm_metrics
- The process exits if the connection is unsuccessful
- The script keeps monitoring for unwanted disconnections and other connection errors and prints an error message
  to the console if encountered
- The application still keeps running even after dosconnection, the application only exists if a subsequent logging
  attempt fails
